# 3) V8 Memory Structure and Garbage Collection Mechanics

## Executive Overview
Node.js processes run inside a memory-managed environment powered by V8's Garbage Collector (GC). Understanding the internal segments of the V8 Heap, the distinction between Young Generation and Old Generation spaces, and the mechanics of the Scavenger and Mark-Sweep-Compact algorithms is critical for preventing memory leaks, reducing GC pause latency, and tuning production servers under high load.

---

## 1. V8 Memory Layout Overview

Total memory allocated to a Node.js process is divided into **Resident Set Size (RSS)**:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      Node.js Process Memory (RSS)                      │
├────────────────────────────────────────────────────────────────────────┤
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │                             V8 Heap                                │ │
│ │  ┌───────────────────────┐  ┌───────────────────────────────────┐  │ │
│ │  │   New Space (Young)   │  │         Old Space (Tenured)       │  │ │
│ │  │  ┌─────────┬────────┐ │  │  ┌───────────────┬─────────────┐  │  │ │
│ │  │  │ Nursery │ From/To│ │  │  │ Old Pointer   │  Old Data   │  │  │ │
│ │  │  └─────────┴────────┘ │  │  └───────────────┴─────────────┘  │  │ │
│ │  └───────────────────────┘  └───────────────────────────────────┘  │ │
│ │  ┌───────────────────────┐  ┌───────────────────────────────────┐  │ │
│ │  │  Large Object Space   │  │     Code Space / Map Space        │  │ │
│ │  └───────────────────────┘  └───────────────────────────────────┘  │ │
│ └────────────────────────────────────────────────────────────────────┘ │
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │                        V8 Stack (Call Frames)                      │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │           Off-Heap / External Memory (Node Buffers, C++ Bindings)  │ │
│ └────────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

### Breakdown of V8 Memory Segments:

1. **New Space (Young Generation)**:
   - Size: Typically 1MB to 64MB (dynamically scaled).
   - Holds newly allocated objects. Most objects in JavaScript have very short lifespans (The **Generational Hypothesis**).
   - Sub-divided into **Nursery** (where new allocations land) and two **Semi-Spaces (From-Space and To-Space)**.
2. **Old Space (Old Generation)**:
   - Holds long-lived objects that survived multiple GC cycles in the New Space (Tenuring).
   - Split into:
     - **Old Pointer Space**: Contains objects that contain references/pointers to other objects.
     - **Old Data Space**: Contains raw data payloads (strings, raw byte arrays, boxed numbers) that cannot point to other objects.
3. **Large Object Space (LOS)**:
   - Holds objects whose size exceeds the page allocation limit (~512KB).
   - Objects here are never moved or compacted during GC cycles to avoid expensive memory copies.
4. **Code Space**:
   - Contains compiled machine code instructions generated by JIT compilers (Sparkplug, TurboFan).
5. **Map Space (Shape Space)**:
   - Contains Hidden Classes (Shapes/Maps) used for property offsets and fast lookups.
6. **Off-Heap / External Memory**:
   - Memory allocated by C++ layers and Node.js native `Buffer` objects (`Buffer.alloc()`, `ArrayBuffer`).
   - Not counted inside `heapUsed`, but tracked in `process.memoryUsage().external` and `arrayBuffers`.

## 2. Inspecting Memory in Node.js

```javascript
// memory-inspection.js
const used = process.memoryUsage();
console.table({
  'RSS (Total Process Memory)': `${(used.rss / 1024 / 1024).toFixed(2)} MB`,
  'Heap Total (V8 Allocated)': `${(used.heapTotal / 1024 / 1024).toFixed(2)} MB`,
  'Heap Used (Actual Objects)': `${(used.heapUsed / 1024 / 1024).toFixed(2)} MB`,
  'External (C++ Bindings)': `${(used.external / 1024 / 1024).toFixed(2)} MB`,
  'ArrayBuffers (Buffers)': `${(used.arrayBuffers / 1024 / 1024).toFixed(2)} MB`,
});
```

## 3. Garbage Collection Algorithms

V8 employs two primary garbage collectors:

### A. Minor GC: The Scavenger Algorithm (Cheney's Copying GC)
- **Target**: New Space (Young Generation).
- **Frequency**: Runs frequently (every few milliseconds to seconds).
- **Execution Speed**: Extremely fast (typically 1ms to 5ms).
- **Mechanism**:
  1. New objects land in the **Nursery** inside New Space.
  2. During a Scavenge cycle, the New Space is divided into two semi-spaces: **From-Space** (active) and **To-Space** (empty).
  3. The collector traces live object roots from the stack.
  4. Live objects in From-Space are copied compactly into To-Space.
  5. Dead (unreferenced) objects are discarded immediately with zero cost.
  6. If an object has already survived one Scavenge cycle, it is promoted (**tenured**) directly to the **Old Space**.
  7. The roles of From-Space and To-Space are swapped.

```text
From-Space (Active)        To-Space (Empty)
┌───┬───┬───┬───┬───┐     ┌───┬───┬───┬───┬───┐
│ A │ ✕ │ B │ ✕ │ C │ ──> │ A │ B │ C │   │   │  (Compacted live objects)
└───┴───┴───┴───┴───┘     └───┴───┴───┴───┴───┘
```

### B. Major GC: Mark-Sweep-Compact Algorithm
- **Target**: Old Space (Tenured Generation).
- **Frequency**: Runs when Old Space reaches dynamically calculated capacity limits.
- **Mechanism**:
  1. **Marking**: V8 traverses the object reference graph from GC Roots (global object, stack frames, DOM/handles). All reachable objects are marked as "live" using a 3-color marking system (White = unvisited, Grey = visited but children unvisited, Black = visited and live).
  2. **Sweeping**: Traverses memory pages and adds dead (unmarked) memory addresses to "free-lists" so new allocations can reuse the space.
  3. **Compacting**: Relocates live objects into contiguous memory blocks to eliminate memory fragmentation. Pointers to relocated objects are updated.

---

## 4. Modern V8 GC Optimizations

Traditional GC algorithms paused the main thread completely ("Stop-The-World"). Modern V8 drastically cuts pause times using:

1. **Incremental Marking**: Major GC marking is divided into small chunks (~1ms) interleaved with JavaScript execution.
2. **Concurrent Marking & Sweeping**: Background C++ helper threads perform marking and sweeping in parallel while the main JavaScript thread continues running.
3. **Idle-Time GC**: V8 utilizes idle periods (when the event loop has no work) to perform garbage collection.

## 5. Controlling V8 Heap Limits in Production

By default, Node.js configures heap limits based on available system memory (~2GB-4GB on 64-bit systems).

### Configuring Memory Limits:
```bash
# Set maximum Old Space to 4GB
node --max-old-space-size=4096 server.js

# Set initial / minimum Old Space to 1GB to prevent early resizing pauses
node --max-old-space-size=4096 --initial-old-space-size=1024 server.js

# Trace Garbage Collection events in terminal
node --trace-gc server.js
```

### Sample `--trace-gc` Output Explained:
```text
[12450:0x55a8f0]   1523 ms: Scavenge 23.4 (32.0) -> 18.2 (32.0) MB, 2.1 / 0.0 ms  (average mu = 0.998, current mu = 0.998) allocation failure
[12450:0x55a8f0]   3410 ms: Mark-sweep 142.1 (160.0) -> 98.4 (160.0) MB, 14.5 / 0.0 ms (average mu = 0.985, current mu = 0.985) finalize incremental marking
```
- `Scavenge`: Minor GC took 2.1 ms, reduced memory from 23.4 MB to 18.2 MB.
- `Mark-sweep`: Major GC took 14.5 ms, collected 43.7 MB of dead objects.
