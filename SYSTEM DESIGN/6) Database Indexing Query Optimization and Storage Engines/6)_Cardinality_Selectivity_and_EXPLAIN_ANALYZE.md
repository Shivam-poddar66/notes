# 6) Cardinality, Selectivity, and EXPLAIN ANALYZE

## Executive Overview
Creating an index does not guarantee the database will use it. The database **Cost-Based Query Optimizer (CBO)** calculates whether traversing an index is cheaper than scanning the entire table based on **Cardinality** and **Selectivity**.

---

## 1. Cardinality vs. Selectivity

- **Cardinality**: The total count of distinct values in a column.
- **Selectivity**: The ratio of distinct values to the total number of rows:
  $$\text{Selectivity} = \frac{\text{Cardinality}}{\text{Total Rows}}$$

```text
EXAMPLE 1: `user_email` (1,000,000 unique emails in 1,000,000 rows)
Selectivity = 1,000,000 / 1,000,000 = 1.0 (Maximum Selectivity!)
* The B+ tree locates the exact single row instantly. Outstanding index candidate.

EXAMPLE 2: `is_deleted` (Boolean: 2 values in 1,000,000 rows)
Selectivity = 2 / 1,000,000 = 0.000002 (Extremely Low Selectivity!)
* If 95% of rows have `is_deleted = false`, reading via index requires traversing
  950,000 leaf pointers plus 950,000 bookmark lookups.
* The query optimizer will deliberately IGNORE the index and perform a Full Table Scan!
```

---

## 2. Deciphering `EXPLAIN` and `EXPLAIN ANALYZE`

Running `EXPLAIN` shows the query execution plan generated by the optimizer.

### Access Types (From Fastest to Slowest):
1. **`const` / `system`**: Retrieves a single row via Primary Key or Unique Index in $O(1)$ (`WHERE id = 1`).
2. **`eq_ref`**: One row read from this table for each row of the preceding table during a Primary Key / Unique join.
3. **`ref`**: Matches multiple rows via a non-unique secondary index.
4. **`range`**: Scans index entries within a bounded range (`BETWEEN`, `>`, `<`).
5. **`index`**: Full Index Scan. Traverses the entire B+ tree from start to finish.
6. **`ALL`**: **Full Table Scan (Worst Performance)**. Reads every physical disk page in the entire table.

---

## 3. Top 4 Index-Killing Anti-Patterns in SQL

### 1. Wrapping Indexed Columns in Functions:
```sql
-- WRONG (Full Table Scan! Optimizer cannot use index on created_at):
SELECT * FROM orders WHERE YEAR(created_at) = 2026;

-- CORRECT (Range scan on B+ tree):
SELECT * FROM orders WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
```

### 2. Implicit Data Type Conversion:
```sql
-- Suppose `phone` is VARCHAR(20)
-- WRONG (Forces string-to-number casting on every row -> Full Table Scan):
SELECT * FROM users WHERE phone = 1234567890;

-- CORRECT:
SELECT * FROM users WHERE phone = '1234567890';
```

### 3. Leading Wildcard in LIKE:
```sql
-- WRONG (Full Table Scan: prefix unknown):
SELECT * FROM users WHERE username LIKE '%alex';

-- CORRECT (Uses B+ tree range scan):
SELECT * FROM users WHERE username LIKE 'alex%';
```

### 4. OR Conditions Across Unindexed Columns:
```sql
-- If column B is not indexed, the entire query falls back to a Full Table Scan:
SELECT * FROM users WHERE indexed_col = 10 OR unindexed_col = 20;
```
